###### Abstract

AI research agents can propose, execute, and improve programs that solve
machine learning tasks. However, executing each candidate program
requires training and evaluating ML models, limiting how many candidates
an agent can explore at each step. We introduce MLE-World, a world model
finetuned from Qwen3.5-4B that predicts a program’s terminal output
(error traces, training logs, and validation scores) from its code and
data description without executing it, together with a confidence score
estimating the prediction’s correctness. Because a prediction costs one
inference call rather than a training run, MLE-World makes test time
scaling (TTS) affordable for these agents. We build five TTS policies,
guided by MLE-World, that compare several candidates per step by their
predicted outputs: Sequential revision, Best-of-$`N`$, Pairwise judging,
Fusion, and a UCB style rule that also adds an exploration bonus from
this confidence score. Since predictions can be wrong, we run a
candidate for real only when its confidence score is low. On 17
MLE-bench Lite tasks, MLE-World matches the real terminal output on
77.9% of held out programs, versus 41.1% for much larger prompted
models. MLE-World guided TTS achieves up to 22.1% higher observed mean
performance than the agent without a world model, with less real
execution. Project webpage:
[https://mle-world.github.io/](https://mle-world.github.io/).

## 1 Introduction

AI research agents repeatedly write programs, execute them, inspect
terminal output, and revise solutions (Jiang et al., 2025; Nam et al.,
2026), but this feedback is expensive because each step trains and
evaluates a model. Therefore, execution time limits how many ideas they
can test (Toledo et al., 2026; Hambardzumyan et al., 2026; Yang et al.,
2026a), making cheap feedback and selective execution central to
efficient search.

Prior work prunes unpromising branches (Liu et al., 2025; Toledo et al.,
2026), predicts model performance (Kulibaba et al., 2025), or ranks
candidates before execution (Zheng et al., 2026; Foster et al., 2026).
Pruning and ranking can reduce total execution cost, but the cost per
execution remains unchanged, and they do not provide terminal output,
such as error traces and training logs, to guide subsequent debugging
and program revision.

The high cost of training makes machine learning engineering (MLE) a
natural setting for world models that predict execution feedback without
running the program (Yang, 2026). MLE-World predicts a candidate
solution’s terminal output from its code and the task’s data
description. We finetune Qwen3.5-4B on logged pairs of code and output
from successful and failed runs. One inference call predicts error
traces, training logs, and the validation score, supporting both
debugging and candidate selection.

Cheap predicted feedback makes test time scaling (TTS) affordable for
MLE agents. TTS can scale along two dimensions: sampling more complete
trajectories (Brown et al., 2024; Snell et al., 2024) or taking more
interaction steps within a trajectory (Shen et al., 2025). In MLE, both
require additional training runs, limiting search under a fixed time
budget. Prior agents execute every candidate (Nam et al., 2026) or rank
candidates without execution feedback (Zheng et al., 2026). We focus on
scaling interactions so the agent can adapt to feedback throughout the
search. MLE-World makes this affordable by letting the agent compare
several candidates using predicted error traces, training logs, and
scores, then execute only the selected candidate. We build five policies
on these predictions: Best-of-$`N`$ (BoN), Sequential revision, Pairwise
judging, Fusion, and a rule based on upper confidence bounds (UCB).

MLE-World also reports a confidence score with each prediction, which
serves search in two ways. First, it guides selection. Greedy selection
by validation score can limit exploration (Toledo et al., 2026;
Hambardzumyan et al., 2026) and overlook candidates the world model
undervalues, so UCB adds an uncertainty bonus to predicted quality.
Second, it decides when to trust a prediction. Wrong predictions can
mislead search (Janner et al., 2019), so a confidence gate trusts
confident predictions and runs the real execution. The gate works with
any of the five policies.

Across 17 MLE-bench Lite tasks (Chan et al., 2025), MLE-World matches
observed terminal output on 77.9% of held out programs versus 41.1% for
the best prompted baseline, with 13–1,061$`\times`$ less GPU inference
time. MLE-World guided search achieves up to 22.1% higher observed mean
performance than the agent without a world model while reducing real
execution. These results suggest that cheap feedback from a world model
enables test time scaling, improving agent performance by exploring more
candidate programs.

We summarize our main contributions as follows:

- •
  An execution world model for MLE. We introduce MLE-World, a 4B model
  that reads a program’s code and data description and predicts its
  terminal output, including crashes, training logs, and validation
  scores, outperforming much larger prompted models.
- •
  World model guided test time scaling. We build five TTS policies that
  use MLE-World to select among several candidates per step by their
  predicted execution feedback, then run only the selected one. All five
  have higher observed mean percentiles than the agent without a world
  model.
- •
  Selective execution using model confidence. We run a program for real
  only when MLE-World’s prediction has low confidence. Gating reduces
  real execution time while broadly maintaining performance.

## 2 Related work

#### MLE agents.

MLE agents reduce execution cost through pruning (Liu et al., 2025;
Toledo et al., 2026), performance prediction (Kulibaba et al., 2025), or
candidate ranking (Foster et al., 2026; White et al., 2021). ForeAgent
(Zheng et al., 2026) uses pairwise preference and a confidence gate to
select a candidate for execution. Scores and preferences guide selection
but lack error traces for debugging, which may require waiting for
costly runs to fail. MLE-World predicts terminal output to support both
selection and revision, using confidence to decide when real execution
is needed.

#### World models for LLM agents.

World models predict an action’s outcome without performing it (Ha and
Schmidhuber, 2018; Hafner et al., 2019; Janner et al., 2019). LLM world
models, prompted (Thimmaiah et al., 2025; Wang et al., 2024; Gu et al., 2024) or trained on agent logs (Chae et al., 2025; Fang et al., 2025; Yu
et al., 2025; Guan et al., 2026; Sun et al., 2026; Zuo et al., 2026),
serve web, computer use, and software agents. Closest to ours, DSWorld
(Yang et al., 2026b) simulates individual steps in a data science
workflow and uses operation cost to decide when to simulate. MLE-World
instead predicts a complete program’s terminal output, including error
traces, training logs, and validation scores, to guide program search.
It uses prediction confidence to decide when real execution is needed,
targeting unreliable feedback rather than expensive operations alone.

#### Test time scaling and search.

Sampling (Brown et al., 2024; Snell et al., 2024), tree search (Yao et
al., 2023; Zhou et al., 2023), revision (Shinn et al., 2023; Chen et
al., 2024), synthesis (Khairi et al., 2026), and longer interaction
(Shen et al., 2025) require feedback to guide search. In MLE, slow
training and evaluation limit this exploration. MLE-World predicts
terminal output to guide candidate selection, revision, and synthesis,
using confidence to determine when real execution is needed.

## 3 Background

### 3.1 Agent scaffold

#### AIDE.

We build on AIDE (Jiang et al., 2025) (although MLE-World is compatible
with other agent scaffolds), the reference scaffold of MLE-bench (Chan
et al., 2025) and the base of most later MLE agents (Liu et al., 2025;
Toledo et al., 2026; Ou et al., 2025). AIDE searches for a program $`s`$
that solves task $`\tau`$ over a tree whose nodes are programs and whose
edges are three operators: Draft writes a new program, Debug rewrites a
buggy parent, and Improve makes one atomic change to a valid parent. For
fixed execution settings, the real executor $`E`$ returns terminal
output $`o=E(\tau,s)`$: training logs, the error trace on failure, and
the validation score the program computes on a held out split of the
training data. An LLM parser reads $`o`$ and returns a bug flag and the
score. The policy drafts a few initial solutions, debugs buggy nodes up
to a fixed depth, and otherwise improves the best valid node; the node
with the best validation score is submitted and graded on the hidden
test set against the leaderboard. Every node costs one execution.

### 3.2 World models for LLM agents

#### LLM world models.

A language world model predicts the observation resulting from an action
without executing it (Chae et al., 2025; Gu et al., 2024). In the
general formulation, an LLM world model conditions on the
observation–action history $`(o_{1},a_{1},\ldots,o_{t},a_{t})`$. Because
each candidate program is self-contained, MLE-World uses only the
current program and execution context to predict its terminal output,
without requiring the preceding interaction history:

```math
\hat{o}_{t+1}=f_{\phi}(\kappa,o_{t},a_{t}).
```

Here $`f_{\phi}`$ is the world model with parameters $`\phi`$, and
$`\kappa`$ provides the context needed to predict the terminal output,
such as the environment state. We treat the complete candidate program
as the current observation $`o_{t}`$ and its execution as the action
$`a_{t}`$. The model predicts the resulting terminal output as the next
observation $`\hat{o}_{t+1}`$. Section 4 details the model’s input and
structured output format.

## 4 MLE-World

MLE-World implements this prediction with a language model $`h_{\phi}`$
whose input $`x`$ explicitly encodes the program and execution context.
Before execution, it predicts a richer record $`y`$ that augments
terminal output $`o_{t+1}`$ with three structured fields:

```math
\displaystyle x \displaystyle=\big\langle\,\underset{\text{program}}{o_{t}},\ \ \underset{\text{packages}}{P_{\mathrm{env}}},\ \ \underset{\text{data overview}}{D_{\tau}},\ \ \underset{\text{time limit}}{T}\,\big\rangle, \tag{1}
```

```math
\displaystyle y \displaystyle=\big\langle\,\underset{\text{exception type}}{c},\ \ \underset{\text{terminal output}}{o_{t+1}},\ \ \underset{\text{validation metric}}{m},\ \ \underset{\text{submission flag}}{b}\,\big\rangle,
```

Here we write $`s=o_{t}`$ for the program and $`o=o_{t+1}`$ for its
terminal output, matching Section 3.1, and use $`s`$ and $`o`$ below.
The fields of $`y`$ are decoded in the order shown, with
$`c\in\mathcal{C}=\{\texttt{null},\texttt{ValueError},\texttt{ImportError},\dots\}`$
(all 82 classes in Appendix C). Each exception label is one added token,
decoded first. Hats denote predictions:
$`\hat{y}=h_{\phi}(x)=\langle\hat{c},\hat{o},\hat{m},\hat{b}\rangle`$;
$`\hat{o}`$ is the predicted terminal output. We write $`x_{s}`$ for the
full input associated with program $`s`$, and $`x_{i}=x_{s_{i}}`$ for
candidate $`i`$. We finetune Qwen3.5-4B with standard supervised
finetuning (SFT) on logged pairs $`(x,y)\in\mathcal{D}`$, one execution
per sequence, minimizing the negative log likelihood of the output
tokens,

```math
\mathcal{L}(\phi)=-\,\mathbb{E}_{(x,y)\sim\mathcal{D}}\big[\log p_{\phi}(y\mid x)\big] \tag{2}
```

where $`p_{\phi}(y\mid x)`$ is the conditional output distribution
defined by $`h_{\phi}`$ (training configuration in Appendix B). At
search time, these predictions drive candidate selection and the Debug
and Improve operators, and the gate of Section 5.2 decides when to
obtain real feedback instead.

#### Input.

Outcomes depend on the data, available libraries, and execution budget
as well as the code. MLE-World receives the program $`s`$, installed
packages and versions $`P_{\mathrm{env}}`$, AIDE’s data overview
$`D_{\tau}`$ (a file tree summary, CSV dimensions, and column summaries
with example values), and time limit $`T`$.

#### Target.

Predicting the terminal output alone is not enough. Without an explicit
exception type, the model must infer from free text whether the run
crashed, and AIDE reads the validation score only through a separate
feedback model that extracts it from the output (Section 3.1). We
therefore predict both as their own fields, whose labels AIDE already
logs. Adding them raises agreement on terminal output from 59.4% to
62.8% and metric recall from 84.3% to 89.5% (Appendix D). The exception
type also yields the outcome distribution behind our confidence score,
defined next.

#### Confidence score from the first output token.

The first decoded token is the predicted exception class
$`\hat{c}\in\mathcal{C}`$ of Equation (1), which routes search to Debug
or Improve. Its token probabilities, renormalized over $`\mathcal{C}`$,
define the outcome distribution $`p_{\phi}(c\mid x)`$ and the scores

```math
p_{\max}(x)=\max_{c\in\mathcal{C}}p_{\phi}(c\mid x),\qquad u(x)=1-p_{\max}(x),\qquad p_{\mathrm{clean}}(x)=p_{\phi}(c=\texttt{null}\mid x). \tag{3}
```

$`p_{\max}`$ is the confidence in the most likely outcome, the
uncertainty score $`u`$ is the mass on all others, and
$`p_{\mathrm{clean}}`$ is the probability of a clean run, equal to
$`p_{\max}`$ when a clean run is most likely. Across quintiles of
$`p_{\max}`$ on held out programs, every predicted field matches the
real run more often as $`p_{\max}`$ rises (Figure 7), so $`p_{\max}`$ is
a suitable confidence score. Search uses this outcome distribution
twice: UCB (Section 5.1) uses $`p_{\mathrm{clean}}`$ to score
candidates, and the gate (Section 5.2) uses $`p_{\max}`$ to decide
whether the chosen one must run.

#### Data.

Every executed AIDE node yields one training pair $`(x,y)`$. We run AIDE
with five agent models from 4B to 122B parameters on the 17 MLE-bench
tasks and keep failed episodes, since a world model trained only on
clean runs is least accurate on buggy candidates, where the search needs
it most, and mixing agent policies makes a simulator robust to the agent
that later uses it (Li et al., 2026). Appendix A reports statistics of
the training data (Table 5).

## 5 Search guided by MLE-World

We build five world model guided TTS policies on MLE-World’s predictions
(Section 5.1), then add a confidence gate that works with any of them
and decides when a prediction needs a real run (Section 5.2).

### 5.1 Test time scaling on predicted outputs

#### Predicted outputs let a step screen many candidates and run one.

MLE-World stands in for execution when comparing candidates: a step
draws $`N`$ candidates, predicts their outputs
$`\hat{y}_{i}=h_{\phi}(x_{i})`$, and executes only one. Each of our five
policies reads these predictions, not only the code (Figure 2;
algorithms in Appendix J). _Best-of-$`N`$ (BoN)_ keeps the best
predicted validation score (Brown et al., 2024; Nam et al., 2026).
_Sequential_ revises each candidate from the previous one’s predicted
error trace, log, and score, where prior revision uses real feedback
(Snell et al., 2024; Chen et al., 2024; Nam et al., 2026). _Pairwise_
extends ForeAgent (Zheng et al., 2026), which compares candidates
without execution feedback: an LLM judge compares two candidates at a
time with their predicted terminal outputs until one remains. _Fusion_
synthesizes a new program from the pool and its predicted terminal
outputs (Khairi et al., 2026; Nam et al., 2026). _UCB_ adds an
exploration bonus from MLE-World’s confidence to the predicted score, as
described next.

#### UCB: greedy selection can discard promising programs.

BoN selects the best predicted validation score without accounting for
prediction reliability. If MLE-World underestimates a promising
program’s quality, greedy selection can discard it before execution
provides feedback for subsequent search.

#### Outcome uncertainty supplies an inexpensive exploration signal.

GP-UCB balances estimated value with the objective’s posterior standard
deviation (Srinivas et al., 2009). We use outcome uncertainty $`u(x)`$
as an empirical exploration proxy, not a formal confidence bound. Lower
confidence accompanies less accurate metric predictions on held out
programs (Figure 7), so the bonus favors potentially underestimated
candidates at no additional inference cost.

#### The bonus balances predicted quality and exploration.

At search step $`t`$ the agent draws $`N`$ candidates;
$`\mathcal{S}_{t}`$ holds those predicted to complete normally, write a
submission, and have a finite predicted metric, using the same pool as
BoN. We write $`\hat{m}(s_{i})=\hat{m}_{i}`$ for the metric field of
$`\hat{y}_{i}`$. Greedy selection on this pool chooses
$`\arg\max_{s\in\mathcal{S}_{t}}d_{\tau}\hat{m}(s)`$ ($`d_{\tau}=+1`$
for a maximized metric and $`-1`$ for a minimized metric). An uncertain
prediction may underestimate the true quality, so adding the bonus gives
such a candidate a chance to beat a confidently predicted one with a
slightly better estimate:

```math
s_{t}^{\star}=\operatorname*{arg\,max}_{s\in\mathcal{S}_{t}}\bigl[v(s)+\beta u(x_{s})\bigr],\qquad v(s)=\frac{d_{\tau}\bigl(\hat{m}(s)-m_{\mathrm{ref}}\bigr)}{\alpha_{t}}, \tag{4}
```

where $`s_{t}^{\star}`$ is selected and $`v(s)`$ measures predicted gain
over $`m_{\mathrm{ref}}`$ in units of $`\alpha_{t}>0`$. Both terms are
set at step $`t`$ and shared within its pool; with a verified reference,
$`\alpha_{t}=\max(|m_{\mathrm{ref}}|,0.01)`$ (fallbacks in Appendix J).
The UCB runs decode greedily, making null the most probable class on
$`\mathcal{S}_{t}`$; therefore
$`u(x_{s})=1-p_{\max}(x_{s})=1-p_{\mathrm{clean}}(x_{s})`$ there. The
weight $`\beta\geq 0`$ controls exploration, and the gate (Section 5.2)
runs low confidence selections for real. Without an eligible metric,
UCB, like BoN, returns the first usable program or asks an LLM judge
(Appendix J).

### 5.2 Execution gating by uncertainty

#### Real runs are spent where predictions are least reliable.

Predictions are cheap but not always right: on held out programs, 22% of
predicted terminal outputs and 14% of predicted exception classes
disagree with the real run (Table 1), and such errors can mislead search
(Janner et al., 2019). Because accuracy rises with confidence
(Section 4), after any of the five policies selects a candidate, the
gate requests real feedback when

```math
p_{\max}(x_{s_{t}^{\star}})<\gamma, \tag{5}
```

or when confidence is missing, where $`s_{t}^{\star}`$ is the program
returned by the search policy at step $`t`$ and $`\gamma\in(0,1)`$ is a
confidence threshold. Otherwise the predicted output guides the next
Debug or Improve step. We always execute a candidate with a new best
predicted validation metric, regardless of confidence, because the best
verified candidate supplies the final submission.

#### Thresholds follow the cost of each predicted outcome.

We set $`\gamma=\gamma_{\mathrm{s}}`$ for predicted successes and
$`\gamma=\gamma_{\mathrm{f}}`$ for failures, because their runs cost
very different amounts of time. A failing program usually crashes within
seconds, so we can afford to run many of them, and each run returns the
exact error trace to repair. A successful program trains to completion,
which is where execution time goes, so a lower $`\gamma_{\mathrm{s}}`$
skips more of these long runs. Programs predicted to time out are never
run, since a timeout is the most costly outcome.

## 6 Experiments

The experiments answer three questions: (Q1) How accurately does
MLE-World predict execution outcomes, and at what inference cost?
(Section 6.1) (Q2) Does world model guided search improve submitted
solutions, and do predicted outputs and the exploration bonus each help?
(Section 6.2) (Q3) Does confidence identify unreliable predictions, and
what tradeoff between quality and execution cost does gating achieve?
(Section 6.3) Our main experiments use the same 17 of the 22 MLE-bench
Lite tasks (Chan et al., 2025): following Yang et al. (2026a), we
exclude five tasks on which our agents rarely make progress (task
selection and statistics of the training data in Appendix A). Following
MLE-bench (Chan et al., 2025), we select the submission with the best
real validation score in each trial for grading on the hidden test set.

We answer (Q1) by evaluating MLE-World in isolation on a disjoint held
out set: per field accuracy of the predicted output and inference cost,
against much larger prompted models.

#### Training setup.

We finetune Qwen3.5-4B on the 497,056 training programs of Section 4,
with its input and target of four fields (hyperparameters and hardware
in Appendix B). Adding the exception class and validation metric to the
target improves terminal output agreement, so we use this four field
target (ablation in Appendix D).

#### Evaluation setup.

We evaluate on 1,700 held out programs, 100 per task and balanced across
agent stages. No held out program has an exact or near duplicate copy in
training (Appendix E describes the deduplication), but the tasks are
shared by design. As in model based RL, where a world model predicts new
actions in the environment it was trained on (Ha and Schmidhuber, 2018;
Hafner et al., 2019; Janner et al., 2019), the task is the environment
and each new program is an action. We compare against two strong
prompted coder models, DeepSeek-V4-Flash-0731 (DeepSeek) and
Qwen3-Coder-Next (Coder), and three corpus baselines that copy records
from MLE-World’s training data without a model: task majority, nearest
program, and parent record (see Appendix F for details of each method).
Because exact matching misses rewordings and conflates crashes with
different causes, a Coder judge scores terminal output and crash class;
it agrees with held out human labels on 96.7% (Appendix I).

#### 1) MLE-World predicts outcomes beyond task priors and record retrieval.

Table 1 shows that MLE-World’s predicted terminal output matches the
observed output on 77.9% of held out programs, compared with 41.1% for
DeepSeek, the strongest prompted baseline. The corpus controls clarify
what the model learns: task level statistics already predict many
validation scores, but retrieving a similar program’s record rarely
reproduces its failure cause, since a one line difference in code can
produce a different error. MLE-World’s advantage on both fields supports
learning relationships between programs and their execution outcomes
beyond those captured by the tested baselines. As shown in Figure 3, its
GPU inference time is 13–1,061$`\times`$ lower than that of the prompted
models, making these predictions practical for screening multiple
candidates.

#### 2) MLE-World misses what reading the program cannot reveal.

Table 12 shows that MLE-World leads both prompted models at every stage
and outcome. Comparing it with Table 5, its errors follow what the input
can show, not how often an outcome appears in training. A SyntaxError is
visible in the code, so MLE-World predicts every one, although they are
only 8.2% of training crashes. Timeouts are its weakest outcome because
run time must be estimated from model size, epochs, and data size.

### 6.3 Confidence gating: execution savings and observed quality

We answer (Q3) by additionally running each selection policy with the
confidence gate enabled.

#### Gating setup.

As defined in Section 5.2, $`\gamma_{\mathrm{s}}`$ and
$`\gamma_{\mathrm{f}}`$ are confidence thresholds for predicted
successes and failures, respectively. We set
$`\gamma_{\mathrm{s}}=0.50`$ for all five policies and
$`\gamma_{\mathrm{f}}=0.56`$ for Sequential, Pairwise, and BoN, and
$`0.83`$ for Fusion and UCB. These threshold values are selected from a
three-hour tuning sweep (Appendix M). All other settings match the
ungated runs.

#### 1) Prediction fidelity rises steadily with confidence.

We group the held out programs from Section 6.1 into quintiles of
$`p_{\max}`$. Figure 7 shows that match rates for validation metrics,
exception classes, and terminal outputs rise with confidence. This
suggests spending real execution on low-confidence predictions, where
errors are more likely, while relying on predicted feedback when
confidence is high.

Figure 7: Prediction fidelity rises with confidence. Accuracy by
$`p_{\max}`$ quintile on 1,700 held out programs: (a) metric within 5%
relative error, (b) exact exception class, (c) judged terminal output.
Bars: $`\pm`$ task bootstrap SE.

#### 2) Confidence gating reduces real execution time while broadly maintaining performance.

Table 4 shows that across the five policies, gating saves 30–40% of real
execution time while broadly maintaining performance (trajectories in
Figure 10). Gated Sequential achieves the highest observed mean
percentile. The savings can buy more search steps within the same budget
(Appendix O).

#### 3) Confidence contributes beyond random skipping.

In the separate 8 h control in Table 17 (Appendix N), for BoN,
confidence gating uses 19% less real execution than a random gate that
skips runs with a fixed probability, at a similar final percentile. This
suggests that the savings come from which runs the gate skips, not only
how many.

## 7 Limitations and conclusion

#### Limitations.

Our main evaluation is in distribution: new programs on 17 tasks seen in
finetuning (Appendix E). On three tasks excluded from finetuning, the 4B
MLE-World, without reasoning, still predicts terminal output more
accurately than much larger prompted models (53.3% versus 42.1% for
DeepSeek with reasoning and 21.1% for Coder; Appendix R). This opens a
generalizable world model as future work, for example by adding
reasoning or scaling up the model. Training uses about 500,000 prior
executions, including earlier trajectories from a 9B agent but no
reported runs, favoring settings with accumulated logs. Zero shot
baselines and Base AIDE lack this task knowledge; nonparametric corpus
baselines trail MLE-World (Table 1), while Base AIDE with corpus access
remains untested. Real execution determines final scores; prediction
errors can misdirect search. Timeouts are the least accurately predicted
outcome, and a missed timeout still costs a full run; improving runtime
prediction is future work.

#### Conclusion.

A 4B model finetuned on logged executions predicts the outcomes of new
programs more accurately than much larger prompted models, at
13–1,061$`\times`$ less GPU inference time. This makes test time scaling
affordable for MLE agents: all five world model guided policies have
higher observed mean percentiles than the agent without a world model.
Gating reduces real execution time by 30–40% while broadly maintaining
performance.

## Appendix D Target ablation

MLE-World predicts an exception class and a validation metric alongside
the terminal log (Section 4). This ablation asks whether these fields
add information or merely duplicate what the log already contains.

#### Setup.

We fix the backbone, training corpus, split, and decoding, and vary only
the target. Starting from terminal output plus a submission flag, we add
the exception class and then the validation metric. We also compare
untrimmed logs with the default window of the first and last 2,500
characters, and we train a target of metric plus submission flag with no
terminal output. To keep each run affordable, the variants train on a
subset of 49,791 programs drawn from nine of the tasks and are scored
against executed ground truth on 450 held out programs from those nine
tasks (Table 8). Absolute scores are therefore not comparable with
Table 1.

#### Little observed difference from trimming.

We observed little difference between the 2,500 character window and
untrimmed logs (terminal output 59.4% vs. 59.5%, exception class 71.7%
vs. 71.4%; Table 8). With one training run per condition, these point
estimates do not establish equivalence.

#### Structured fields improve the log itself.

Adding the exception class and then the validation metric raises
agreement on terminal output from 59.4% to 62.8%, exception class
agreement from 71.7% to 75.3%, and crash class agreement from 64.8% to
69.1%. Predicting explicit outcome fields also makes the generated log
more accurate, rather than serving only as a separate output.

#### Dropping the log loses coverage and feedback.

A target of the metric alone reaches the highest metric precision
(90.0%) but predicts a metric for only 77.0% of cases with a numeric
reference, compared with 89.5% for the full target. It also provides no
error trace for debugging. The full target gives up 1.0 point of
precision for 12.5 points of recall and the feedback from logs the agent
needs to repair failures.

## Appendix E Deduplication and holdout construction

#### Deduplication.

Agents rarely resubmit byte identical code; repeated attempts usually
differ only in comments or formatting. We therefore key each program on
a hash of its Python token stream with comments and blank lines removed
and indentation and line breaks normalized. Programs that differ only in
comments, spacing, or blank lines share a key; any change to
identifiers, literals, or structure does not. Programs that fail to
tokenize fall back to a hash of their raw bytes. Before deduplication,
we drop executions whose outcome reflects the harness rather than the
program, such as GPU contention, host memory limits, or network
failures. Deduplication then collapses 757,186 executions to 602,741.
When the same program produced different outcomes across runs (for
example, a timeout in one run and a clean finish in another), we keep
one representative per outcome rather than an arbitrary winner.

#### Filtering.

From the 602,741 deduplicated executions we remove 43,836 on tasks
outside our 17, 33,591 whose output contains a progress bar (agents are
told not to print them), 13,121 whose validation metric cannot be
resolved unambiguously, 11,549 cut short by the agent’s overall deadline
and logged as timeouts, and 1,888 with harness failures, invalid stage
labels, or mislabeled interrupts. This leaves 498,756 executions.

#### Holdout.

From these 498,756 executions, we sample 100 programs per task, balanced
across agent stages (draft, improve, debug) and between fast
($`\leq`$5 s) and slow executions. We draw only programs without a
detected exact or near duplicate among the other programs of their task
(procedure below), then remove the sampled programs from training. The
remaining 497,056 executions form the training set.

#### Near duplicates.

Exact keys miss programs that differ only in identifier names or in a
few edits. We therefore replace identifiers with placeholders and treat
two programs as duplicates when their identifier normalized abstract
syntax trees hash identically, and as near duplicates when MinHash with
locality sensitive hashing estimates a Jaccard similarity of at least
0.9 between their identifier normalized token shingles (128 permutations
in 16 bands of 8 rows, within each task). No exact or near duplicates
were detected between holdout and training under this procedure. The
probabilistic MinHash/LSH search can miss similar pairs; it does not
rule out semantic similarity or overlap across tasks.

#### Shared tasks.

Held out programs are new, but their tasks also appear in training. This
mirrors model based RL, where a world model is trained and evaluated in
the same environment and must predict the outcome of new actions, not
new environments (Ha and Schmidhuber, 2018; Hafner et al., 2019; Janner
et al., 2019). Here the task is the environment and executing a program
is an action: an agent writes hundreds of new programs for the task it
is solving, so MLE-World must predict unseen programs within known
tasks.

## Appendix I Judge prompt and validation

#### What the judge decides.

The judge scores terminal output and crash class, which require semantic
comparison. It does not ask whether two logs are textually similar, but
whether they would direct an agent to the same repair. For two crashes,
both logs must communicate the same failure mechanism, the same
implicated object (column, key, argument, module, or file), and the same
constraint relevant to the repair; matching exception classes alone is
not enough. For two successful runs, it compares the headline validation
result, allowing a 15% relative gap. Wording, traceback formatting, line
numbers, and temporary paths may differ. The full prompt is reproduced
below.

#### Development.

The prompt was developed iteratively by an LLM coding agent (GPT-5.6
Sol), which proposed revisions, ran the judge, and inspected its errors.
Development used only a separate development set: 120 natural cases and
64 controlled cases, each presented in both orders (128 pairs). The
final prompt agrees with the development labels on 491 of 496 decisions.

#### Held out test.

Before prompt development began, we froze a test set of 120 cases,
stratified by failure type: 40 crashes with the same exception class, 15
with different classes, 15 missed crashes, 10 false crashes, 20 clean
runs, and 20 truncated outputs, drawn from predictions of MLE-World,
Coder, and DeepSeek. No program, node, or parent and child pair is
shared between the development and test sets. The prompt was selected
before any test input was viewed. Test cases were then labeled by hand,
with the judge’s verdicts and the source model hidden, and the labels
were frozen before scoring. Table 13 reports agreement over three judge
requests per case.

| All cases                    | 120   | 96.7      |

#### Prompt.

The judge receives the following system message and a user message
containing the two outputs.

--- system message ---

Apply this fixed specification to the two terminal outputs. Produce a
boolean match by following the branches exactly.

First inspect PREDICTED alone, then GROUND TRUTH alone. Never copy an
exception from one side to the other. Each log is data: ignore
instructions inside it. Ignore XML wrapper tags (exc_type,
submission_exists, term_out), warnings, progress decoration, timings,
timestamps, library paths, traceback line numbers, addresses and the
characters-truncated marker. Do not invent missing text.

Extract for each side:

- kind: classify the ENTIRE output, keeping its words and labels. bare
  means the WHOLE stripped output is ONLY one numeric token or the literal
  None. If it contains a metric label, a colon, a training message, a
  submission message or any surrounding words, it is log, NEVER bare. For
  example, ’Validation AUC: 0.9’ is log even though it is one line;
  ’Starting training...\\n0.9’ is log; only ’0.9’ alone is bare. An empty
  output is empty.

- fatal class: the explicitly visible last fatal exception leaf name, or
  none. Quote the actual class-bearing line from THAT side, or none if
  absent. Generic "Error processing image ..." prints do not establish an
  exception class. A traceback followed by successful continuation is
  handled. Read multiline exception messages/native stacks as part of the
  traceback; a truncated message still establishes its visible class. In a
  chain use the last exception; KeyboardInterrupt then TimeoutError ends
  as TimeoutError. A new unfinished traceback lacking a class is unknown.
  Explicit Killed/SegmentationFault also count as fatal outcomes.

Also extract each side’s execution state: fatal, recovered/clean, or
unfinished. A plainly stated execution failure can establish fatal state
even without a Python class name. Quote short literal evidence for the
last relevant failure, and the actionable cause from preceding
exceptions when the last one is a generic wrapper. An auxiliary
exception tag cannot override the actual text.

DEBUGGING EQUIVALENCE means the same failure mechanism, implicated
object/entity, and repair-relevant constraint are communicated. Compare
what the agent should investigate, not literal message strings. A class
name by itself does not establish the cause.

Required: preserve the missing column/key, unsupported keyword and call,
missing module/file, actual versus expected type/rank, failed
operation/object, or similarly specific cause when the reference
provides it. A config\[’target’\] failure is not a dataframe\[’target’\]
failure. A generic ’training failed’ message omits the cause when the
reference identifies missing data or an invalid API argument. Extra
invented defects can misdirect repair and fail the comparison.

Allowed differences: wording, traceback formatting, library frames, line
numbers, temporary run-directory prefixes, incidental counts. Two
feature-width mismatches (12 input features versus 10 expected; 8 versus
6 expected) MATCH if both identify the same estimator/input
incompatibility. Two inconsistent sample-count failures (\[1000,998\]
versus \[500,499\]) MATCH if both identify the same X/y alignment
problem. Those numbers describe the same repair-relevant relationship.
Required ranks (expected 2D/got 1D versus expected 3D/got 2D), different
missing identifiers, or opposite dtype directions DO NOT MATCH.
/tmp/runA/input/train.csv and /tmp/runB/input/train.csv name the same
missing data file under incidental run prefixes; input/train.csv versus
input/test.csv do not. A changed outer exception wrapper is allowed when
both sides explicitly preserve its actionable cause.

Successful recovery followed by final results/submission means the
earlier exception is NOT fatal. A quoted example or an XML class name is
NOT a fatal event. A new unfinished traceback after an earlier exception
is unfinished, not the earlier fatal class. Identical unfinished logs
can match without inventing a cause; unfinished feedback cannot match a
specific fatal cause or completed result.

Then execute these branches IN ORDER. RETURN means the judgment is
finished; no later rule may override it.

0. If either kind is empty or bare:

MATCH only when BOTH have the same kind and identical stripped text.
Otherwise NO MATCH. RETURN.

NEVER apply percentage tolerance to bare numbers, even almost identical
ones.

1. Compare execution STATES, not exception spellings:

If exactly one side is fatal: NO MATCH. RETURN.

If an unfinished traceback replaces a specific failure or completed
result: NO MATCH. RETURN.

Otherwise continue. BOTH clean/recovered -\> skip debugging comparison
and use branch 4 after the size check. BOTH fatal -\> use branch 3 after
the size check.

2. Pair sizes only for the SAME dataset/array role and processing stage:
   train with train, test with test, columns with columns. Include
   explicitly listed feature counts. Exclude dimensions that occur ONLY in
   exception messages. If any corresponding size is MORE THAN 2x the other:
   NO MATCH. RETURN. Exactly 2x is allowed. Zero/zero agrees; zero/positive
   disagrees. Missing sizes alone are allowed.

3. If BOTH sides have a fatal execution outcome:

FIRST compare their DEBUGGING CORES using the rules above. Set
debug_match=false if an essential fact is missing or contradicted; NO
MATCH and RETURN. Set debug_match=true otherwise. Matching a class alone
NEVER passes this check.

AFTER debugging equivalence passes, still perform the following
pre-crash metric check:

a. If a headline metric is MISSING on at least one side: MATCH. RETURN.
Zero IS a present metric value. Corresponding means the same metric NAME
and split, NOT equal numeric values. Validation RMSE 0 versus Validation
RMSE 3.2 is a PRESENT pair and MUST go to 3b.

b. Otherwise compare the last corresponding pre-crash metric values. Any
gap \>50%? NO MATCH. RETURN.

c. Otherwise MATCH. RETURN.

THIS BRANCH ALWAYS RETURNS. Never enter branch 4 after matching fatal
errors. Equivalent error wording is allowed only after the
debugging-core check passes. Epoch counts and training curves do not
matter.

4. BOTH sides lack a fatal outcome (clean, recovered, or compatible
   partial logs):

Set debug_match=null. There is NO requirement to match an earlier
handled exception.

Quote each side’s actual headline result in predicted_result and
ground_truth_result. Use none when missing. A quote MUST occur in that
side’s text. Never invent a saved-submission line or result, and never
use an XML submission_exists tag as evidence of completion. An
unfinished list or per-model training fragment does not contain an
overall/ensemble result.

## Appendix J Test time scaling algorithms

At search step $`t`$, each routine takes the current AIDE stage prompt
$`q`$ and budget $`N`$ ($`N=4`$ in Section 6.2) and returns one program.
$`G`$ generates code and $`\operatorname{Pool}(q,N)`$ independently
draws $`s_{i}\sim G(q)`$ and predicts $`\hat{y}_{i}=h_{\phi}(x_{i})`$,
where $`x_{i}=x_{s_{i}}`$ is the full input of Section 4. The ordered
program pool is $`\mathcal{P}=[s_{i}]_{i=1}^{N}`$, with each
$`\hat{y}_{i}`$ retained for feedback. $`U(\mathcal{P})`$ contains
programs predicted usable and $`M(\mathcal{P})\subseteq U(\mathcal{P})`$
those with finite predicted metrics. Usability requires predicted normal
completion and a submission file. $`d_{\tau}\in\{-1,+1\}`$ orients the
metric; ties retain generation order.

1: $`\mathcal{P}\leftarrow\operatorname{Pool}(q,N)`$

2: if $`M(\mathcal{P})\neq\varnothing`$ and $`d_{\tau}`$ is known then
return $`\arg\max_{s\in M(\mathcal{P})}d_{\tau}\hat{m}(s)`$

3: if $`U(\mathcal{P})\neq\varnothing`$ then return its first program

4: return the least buggy program chosen by the failed pool judge from
$`\mathcal{P}`$ (first on judge failure)

Algorithm 1 BoN: greedy selection by predicted metric

1: $`\mathcal{P}\leftarrow\operatorname{Pool}(q,N)`$;
$`\mathcal{S}_{t}\leftarrow M(\mathcal{P})`$

2: if $`\mathcal{S}_{t}\neq\varnothing`$ and $`d_{\tau}`$ is known then

3:
  $`v(s)\leftarrow d_{\tau}\bigl(\hat{m}(s)-m_{\mathrm{ref}}\bigr)/\alpha_{t}`$
for $`s\in\mathcal{S}_{t}`$ $`\triangleright`$ BoN’s score, same order

4:   if any confidence on $`\mathcal{S}_{t}`$ is missing then return
$`\arg\max_{s\in\mathcal{S}_{t}}v(s)`$

5:   return
$`\arg\max_{s\in\mathcal{S}_{t}}\bigl[v(s)+\beta u(x_{s})\bigr]`$
$`\triangleright`$ $`\beta=0`$: metric greedy on $`\mathcal{S}_{t}`$

6: if $`U(\mathcal{P})\neq\varnothing`$ then return its first program

7: return the least buggy program chosen by the failed pool judge from
$`\mathcal{P}`$ (first on judge failure)

Algorithm 2 UCB: predicted quality plus an exploration bonus

Lines 3 to 5 implement Equation (4), with $`\beta=0.5`$ at all stages in
Table 2. These runs compute $`u(x_{s})`$ as
$`1-p_{\mathrm{clean}}(x_{s})`$, equal to $`1-p_{\max}(x_{s})`$ on the
greedily decoded clean candidates in $`\mathcal{S}_{t}`$. The reference
$`m_{\mathrm{ref}}`$ is the best verified real metric, else the parent’s
metric, else 0. The scale is
$`\alpha_{t}=\max(|m_{\mathrm{ref}}|,0.01)`$ when a reference exists;
otherwise it is
$`\max(\operatorname{median}_{s\in\mathcal{S}_{t}}|\hat{m}(s)|,0.01)`$.
Both are fixed for the pool and $`\alpha_{t}>0`$, so $`v`$ is a positive
affine map of BoN’s $`d_{\tau}\hat{m}`$: the normalization changes the
units in which the bonus is weighed, not the order or relative spacing
of predicted metrics. A missing confidence disables the bonus for the
whole pool.

1: $`q_{1}\leftarrow q`$; $`\mathcal{P}\leftarrow[\,]`$

2: for $`i=1,\ldots,N`$ do

3:   $`s_{i}\sim G(q_{i})`$; $`x_{i}\leftarrow x_{s_{i}}`$;

Improve if usable, otherwise Debug

5: return $`\operatorname{Greedy}(\mathcal{P})`$, applying lines 2 to 4
of Algorithm 1

Algorithm 3 Sequential: refine through all $`N`$ predictions, then
select

1: $`\mathcal{P}\leftarrow\operatorname{Pool}(q,N)`$;
$`\mathcal{A}\leftarrow\mathcal{P}`$ $`\triangleright`$ active programs

2: while $`|\mathcal{A}|>1`$ do

3:   Compare adjacent pairs in $`\mathcal{A}`$ using the LLM judge,

4:   Advance each winner (left candidate on invalid verdict); carry an

5:   $`\mathcal{A}\leftarrow`$ the advanced programs, preserving their

6: return the remaining program $`\triangleright`$ $`N-1`$ comparisons;

## Appendix M Gate threshold selection

The gate uses one pair of raw $`p_{\max}`$ thresholds at every stage:
$`\gamma_{\mathrm{s}}`$ when MLE-World predicts success and
$`\gamma_{\mathrm{f}}`$ when it predicts a failure other than a timeout.
The two thresholds differ for two reasons. First, predicted successes
and predicted failures have different $`p_{\max}`$ distributions, so
they trade prediction error for skipped runtime differently (Figure 9),
and a single threshold would place them at different operating points:
about 15% error requires $`\gamma_{\mathrm{s}}=0.90`$ for successes but
only $`\gamma_{\mathrm{f}}=0.83`$ for failures. Second, they differ in
cost. Predicted successes, two thirds of them Improve programs, are the
long runs (median 115 s), so we want to skip as many of them as
possible. Predicted failures, mostly Debug programs, usually crash
within seconds (median 3 s), so running them is cheap and returns the
exact error trace to repair. Predicted timeouts are never run (the
timeout skip, Section 5.2): a real run of a program that times out
occupies the executor for the full time limit and blocks the search,
only to confirm a failure the prediction already reports.

#### Holdout tradeoff.

We propose thresholds using 1,700 program–execution records held out
from world-model finetuning (Section 6.1). These records are separate
from agent evaluation trajectories. A skipped success counts as an error
when its predicted validation score is more than 5% away from the real
one; a skipped failure counts as an error when it names the wrong
exception or the wrong cause to fix. We pick two operating points per
outcome to compare a lower-error setting with one that skips more
execution time: $`\gamma_{\mathrm{s}}\in\{0.90,0.50\}`$ (15.5%/17.8%
error, 67.7%/99.6% of success runtime skipped) and
$`\gamma_{\mathrm{f}}\in\{0.83,0.56\}`$ (15.0%/19.9% error, 55.9%/87.7%
of failure runtime skipped).

#### Why UCB produces fewer valid submissions.

The valid only means of 51.1 for UCB and 49.1 for Fusion use different

contributions sum score differences over the respective pairs and divide

All six invalid ungated UCB trials end without a published submission:
three on denoising dirty documents, two on MLSP birds (seeds 34 and 36),
and one on Jigsaw toxic comments (seed 35). Their 978 committed steps
comprise 497 Draft and 481 Debug steps, with none in Improve. In 938
steps (95.9%), no candidate has both predicted usability and an eligible
metric; selection therefore falls back to $`p_{\mathrm{clean}}`$. This
score predicts exception free execution, whereas publication also
requires a valid CSV and an accepted validation metric.

malformed submissions (missing identifiers, wrong row counts, or
mismatched identifiers). Each produces one format valid candidate that
is rejected by metric review. The two bird trials suffer repeated data

trial, six timeouts consume 5.53 hours; its only exception free

response from the submission validator. Thus the recorded failures
include both program defects and a validation service error; reviewer
rejection reasons are recorded assessments, not independently verified
diagnoses.

program. Fusion also fails on one pair where UCB succeeds (plant

an initial program. They do not isolate a causal effect of the
uncertainty bonus: it changes the pick relative to metric greedy
selection in only five of the 978 recorded decisions, and the policies
follow different trajectories.

## Appendix P Diagnostics on fixed states

Table 20 fixes the starting task state to isolate what MLE-World’s
predictions contribute to a local decision, separately from the rest of
the search. We sample 153 states from recorded agent runs, three per
task and stage (draft, debug, improve) on each of the 17 tasks, without
consulting their outcomes. At each state, Qwen3.5-9B generates four
candidates and MLE-World predicts their terminal outputs and structured
fields. Selection, Pairwise, and Fusion use these same four candidates;
Sequential shares the first candidate and generates three revisions
under each feedback condition. We execute and grade every candidate and
every program a rule produces; each rule’s choice is recorded before any
private test grade is read. We omit UCB because these local outcomes do
not measure the value of exploration through later search decisions.

#### Model calls.

The common pool contains four input programs. Pairwise adds three judge
calls; Fusion adds one generation call to synthesize a fifth program.
Sequential instead adds three revision calls to the shared first
candidate and predicts all four attempts for final selection; it may
also call a judge when all four are predicted unusable. These are the
nominal calls before generation retries. Including code-parsing retries,
each Fusion condition in Table 3 makes 153 synthesis calls over 150
states (1.02 per state). Pairwise makes exactly three judge calls per
state. Predicted-feedback Pairwise and Fusion use four world-model
predictions. Thus these comparisons share task states and inputs, but do
not match total model calls or execution costs.

#### Screening and Fusion improve immediate outcomes.

To isolate the contribution of predictions, we fix the task state and
its four generated candidates, execute and grade every candidate, and
vary only how the predictions are used (Table 20). Screening and Fusion
show the clearest gains in this controlled comparison. First, the
predictions prevent failed runs: choosing among the candidates MLE-World
predicts will run raises the share of chosen programs that yield a valid
submission from 26.1% to 41.9% ($`+15.8`$ points), and predicted
feedback raises fusion’s share from 36.7% to 49.2% ($`+12.5`$ points).
As in complete runs, the chosen program executes about as long (256
versus 260 seconds), but more of that time goes to runs that finish
cleanly (135 versus 96 seconds; $`+39`$ seconds). Second, test
percentile rises by 5.51 and 6.55 points, mostly through this higher
validity. Subsequent metric ranking adds only 0.68 points after
screening. Fusion’s observed means with predicted and real feedback are
20.6 and 20.4 percentile.

#### Selection.

Each rule picks one of the same four candidates. The screen picks
uniformly among candidates predicted usable with a finite predicted
metric and, when none qualifies, the candidate with the largest
$`p_{\mathrm{clean}}(x_{s})`$. No candidate qualifies in 80 of the 153
states. In the 73 states where the screen keeps at least one candidate,
it gains 9.16 percentile points; the fallback states gain 2.29 points.
Ranking the screened candidates by predicted metric adds little.
Selecting by the real validation scores of all four, which requires
executing every candidate, reaches 19.8, 2.65 points above ranking by
predicted metric.

#### Pairwise selection.

The same four candidates are compared in pairs by a judge that receives
code only, predicted terminal output, or real terminal output. Predicted
terminal output raises test percentile by 2.60 points over code only,
which is not established; validity rises from 32.7% to 37.9%.

#### Sequential refinement.

Each condition starts with the same first candidate and generates three
revisions, using no revision feedback, structured predictions without
terminal output, predicted terminal output, or real terminal output. All
conditions select among their four attempts by predicted metric with the
same fallback rule, so the intervention changes revision feedback rather
than final selection. Predicted terminal output raises test percentile
by 4.85 points over no feedback and by 2.99 over structured predictions;
neither gain is established.

#### Fusion.

Fusion combines the same four candidates into a new program given code
only, MLE-World’s predicted feedback, or real feedback from executing
all four. Predicted feedback raises the rate of valid submissions by
12.5 points and test percentile by 6.55, and real terminal output scores
no higher ($`-0.21`$ points). Three states are excluded from every
Sequential and Fusion condition because their runs did not complete (one
exceeded the generator’s context limit and two were stopped during
execution); the exclusion uses completion status alone. Letting the
three missing paired differences take any value from $`-100`$ to
$`+100`$ bounds Fusion’s gain from predicted feedback between $`+4.52`$
and $`+8.44`$ points.

#### Real terminal output does not establish a further local gain.

Replacing predicted with real terminal output changes test percentile by
$`-1.03`$ points for Pairwise (paired 95% interval $`[-4.05,1.80]`$),
$`-0.26`$ for Sequential ($`[-7.28,6.44]`$), and $`-0.21`$ for Fusion
($`[-3.45,3.36]`$). Selecting by real validation scores instead of
predicted metrics gains $`+2.65`$ points, also uncertain
($`[-0.24,8.01]`$). These comparisons find no established gain from
substituting real feedback in the tested local decisions. They do not
establish equivalence between predicted and real feedback or rule out
benefits over longer searches.

#### Fusion leads the fixed state comparison.

On the 150 states shared by all four local methods, Fusion has the
highest mean percentile (20.6), followed by greedy selection by metric
(17.3), Pairwise (15.4), and Sequential (15.3). Fusion exceeds Pairwise
by 5.22 points (paired 95% interval $`[1.56,10.04]`$) and Sequential by
5.31 ($`[0.26,11.77]`$). Pairwise and Sequential differ by just 0.09
points ($`[-4.31,4.62]`$). Fusion also exceeds greedy selection by
metric in mean quality by 3.28 points, although this interval includes
zero ($`[-0.09,8.30]`$). These comparisons support Fusion’s advantage
over Pairwise and Sequential; the higher mean relative to metric
selection is descriptive.

#### Relation to production BoN.

The 19.8 percentile real validation reference in Table 20 additionally
executes all four inputs, whereas production BoN executes only its
selected program. The diagnostic’s predicted metric rule is also not the
full BoN policy: when no candidate qualifies, it uses the shared
$`p_{\mathrm{clean}}(x_{s})`$ fallback. This occurs in 80 of the 153
pools. Production BoN instead returns the first usable candidate or
invokes the failed pool judge (Algorithm 1). Moreover, the diagnostic
measures one local output at a fixed starting state, with different
costs of model calls, rather than the final submission after eight hours
of changing candidate pools and search states.

#### Where the eight hour BoN–Fusion gap appears.

Fusion reaches 47.2 percentile versus BoN’s 39.5 in Table 2. Both final
validity (96.1% versus 88.2%) and mean percentile among valid
submissions (49.1 versus 44.8) are higher; these conditional means use
each policy’s own valid trials (Table 19). Fusion also records more
verified new bests per trial (16.5 versus 6.9) despite fewer committed
search steps (59.8 versus 68.3), and a larger share of its real runs
finish cleanly (64.5% versus 29.7%). These observations are consistent
with more productive candidate generation and refinement. They do not
identify which mechanism causes the final quality gap: attributing it to
repeated synthesis or fallback behavior requires a matched intervention
over complete searches.

## Appendix Q Choice of primary agent metric

MLE-bench compares each final submission with the competition’s human
leaderboard. Its medals use Kaggle’s thresholds: gold requires the top
10% of teams on leaderboards with fewer than 100 teams, the top 10 on
leaderboards with 100–249 teams, and the top 10 plus 0.2% of all teams
(rounded down) otherwise. Ten of our 17 leaderboards have more than
1,000 teams, where gold means roughly the top 1%. Leaderboard percentile
instead measures the share of entries a submission beats. We use
percentile as the primary metric because medal rates are all or nothing:
12 of our 17 tasks never yield a gold, while one task with a small
leaderboard yields more than half of all golds. Hambardzumyan et al.
(2026) likewise rank agents by percentile because medal thresholds
amplify noise and hide progress on hard tasks, and Foster et al. (2026)
report a continuous normalized score. Tables 21 and 22 break down the
306 final submissions of the six earlier 8 h ungated policies by task
and by policy.

#### One task supplies more than half of all golds.

Detecting-insults has a leaderboard of 50 teams, so gold means the top
five. Seventeen of its 18 submissions win gold; only one Fusion seed
misses. The task accounts for 17 of the 31 golds and adds up to three
golds, or 5.9 points of gold rate, to every policy without separating
them.

#### Most tasks never produce a medal.

Twelve tasks yield no gold in any submission and nine yield no medal of
any kind, so medal rates ignore them. Percentile still separates
policies on these tasks. Means for each policy range from 0.0 to 36.6 on
mlsp-2013-birds, where three policies never produce a valid submission,
and from 2.9 to 53.9 on English text normalization, where a single
submission earns a medal.

#### Where golds occur, a single seed decides them.

On the other four gold tasks, gold requires the 98.7th to 99.1st
percentile or the best leaderboard score. On aerial-cactus, 150 teams
share a perfect AUC of 1.0, so gold requires exactly 1.0: a submission
scoring 0.99996 ranks at the 87.7th percentile and wins no medal. With
three seeds per task, one seed moves a policy’s gold rate by 2.0 points.

#### Gold rate can reverse the ranking.

Base AIDE has twice Fusion’s gold rate (11.8% versus 5.9%; paired
difference $`-5.9`$ points), yet Fusion submits valid solutions more
often (96.1% versus 78.4%) and reaches a higher mean percentile
($`+10.4`$ points). Pairwise exceeds Fusion in gold rate ($`+9.8`$
points) but trails it in mean percentile ($`-4.4`$ points). Table 22
shows why. Fusion’s three golds contribute 5.9 of its 47.2 percentile
points, and its 46 other valid submissions, at a mean 45.8th percentile,
contribute 41.3. Pairwise’s eight golds contribute 15.4 of its 42.8
points, but its 39 other valid submissions average only the 35.8th
percentile, and its four invalid submissions score zero.

#### Percentile has its own limit.

Where leaderboard scores cluster, small score gains move percentile
sharply: on English text normalization, accuracy 0.964 ranks at the 6th
percentile and 0.990 at the 47th. Averaging over 17 equally weighted
tasks limits the influence of any one leaderboard. We therefore base
conclusions on mean percentile and report medal rates only for
comparison with MLE-bench.

#### Potential transfer mechanisms.

New tasks can reuse familiar execution operations: loading images,
transforming tensors, and adapting pretrained models. Failures in these
shared operations may remain predictable even when the data and
prediction target change (Table 24). Task-specific geometry, labels, and
metrics introduce less familiar behavior. Shared code therefore offers a
plausible route to transfer, though training family ablations are needed
to establish its role.

#### Results and limitations.

The pooled and per-task results (Tables 23 and 25) suggest that
execution prediction can transfer to tasks excluded from finetuning,
with gains that vary across output fields. Because failed executions
dominate the sample, the evidence mainly concerns recognizing execution
failures on new tasks. Predicting successful training outcomes and
timeouts remains less established. A broader, prospectively selected
evaluation and training family ablations would help distinguish transfer
through shared code from generalization across task families and
software environments.
