# DRVEXO-4B-Unified: Design and Evaluation of a Modular Speech–Vision System

Zeyuan Li Affiliation: Yujie Intelligence Affiliation: Hangzhou, China
Email: [lizeyuan@drvexo.com](mailto:)

November 7, 2026

###### Abstract

We present DRVEXO-4B-Unified, a modular multimodal assistant built
around a 4B language backbone. A self-contained checkpoint combines
text, image, and speech inputs with reference-conditioned speech output
and structured interaction. A temporal residual connector adapts
acoustic sequences to the language interface; explicit text boundaries
support incremental speech synthesis; and three task-conditioned scoring
heads rank supplied action candidates alongside generative tool calls.
These interfaces connect conversation to application-defined choices
while leaving action authorization to the application. The system
obtains 74.22% on all 900 MMMU validation questions, exceeding the
published validation scores of Gemma 3 4B IT and InternVL3.5-4B without
test-time scaling. Strict prompt-level IFEval accuracy is 82.26% and
MATH-500 accuracy is 89.40%, above the original Qwen3-4B non-thinking
report’s 81.2% and 84.8%, respectively. On NVIDIA GB10, the model
achieves a speech-synthesis first-chunk latency of 390 ms. For
concurrent text generation, a growth-aware admission policy completes a
128-answer batch at 594.41 output tokens/s, including filling and
draining, without preemptions. We plan to release the model weights and
accompanying code under Apache License 2.0, retaining applicable
third-party terms.

Keywords: multimodal systems; speech interfaces; visual reasoning;
evaluation protocols; inference scheduling

## 1 Introduction

An assistant for a physical application must connect communication with
a constrained action space. A user may speak about an image, refer to an
earlier turn, or request one of several available actions. These
operations require different interfaces: perception produces
representations, language generation produces an explanation, speech
synthesis produces a waveform, and candidate scoring ranks supplied
alternatives. Their integration raises a basic evaluation problem.
Successful loading, a correct textual answer, intelligible speech, and a
permissible device action are separate outcomes; one cannot stand in for
the others.

DRVEXO-4B-Unified is developed by Yujie Intelligence for research on
conversational interfaces to assistive-exoskeleton applications. It
combines Qwen3.5-4B visual-language components, Qwen3-ASR acoustic
components, and Qwen3-TTS speech generation with a temporal connector
and task-specific scoring heads \[14, 11, 16\]. The label “4B” denotes
the language backbone. The complete checkpoint stores approximately 6.97
billion scalar tensor elements across its eight components, including
speaker state and other buffers; this storage count is not a
deduplicated trainable-parameter count. Comparisons with models having
approximately 3–4B-class language backbones therefore concern backbone
scale, rather than equal total system size. The target application
motivates the interfaces, but this report does not evaluate a clinical
intervention or autonomous device policy.

Qwen3-Omni studies multimodal understanding and generation through a
jointly trained architecture, with separate task evaluations and a
controlled study of modality retention \[20\]. Composing pretrained
components raises a related question: which capabilities can be
established for the assembled system, and under which measurement
conditions? In DRVEXO-4B-Unified, inherited foundations supply the
visual-language and speech components, while generated text conditions
the active speech-output route. This modular setting calls for explicit
interface specifications and evaluation of the resulting system,
including controls that distinguish inherited capability from local
adaptation.

Figure 1 summarizes the interaction interfaces. Text, images, and speech
enter through their respective input paths; responses can be returned as
text, segmented speech, or structured outputs. Reference recordings
provide speaker conditioning, while candidate sets define the
alternatives to be ranked. These interfaces allow an application to
combine conversation with explicit action choices without treating a
generated explanation as an execution command.

The system combines three interaction choices: temporally resolved
speech input, generated-text boundaries for streaming speech and
reference-voice conditioning, and separate interfaces for free-form tool
generation and supplied-candidate ranking. The report examines these
choices through component specifications, public task results,
comparison with published model reports, and measurements of inference
capacity and reference-runtime speech delivery. Section 2 describes the
model, and Section 3 presents training and checkpoint assembly.
Section 4 defines the experimental questions and measurement protocols.
Section 5 analyzes the results, followed by the limitations in
Section 6. We plan to release the model and accompanying code under
Apache License 2.0, with upstream attribution and applicable third-party
terms retained.

## 2 Model Design

The system uses explicit interfaces between perception, language, speech
generation, and application decisions. Acoustic features pass through a
trainable temporal connector before entering the language space. Images
use the inherited visual projection. Generated text forms the boundary
between language reasoning and speech synthesis, allowing the same
response to be inspected, delivered as text, or segmented for speech.
Candidate scores form a separate output interface because ranking
supplied actions and generating an explanation have different
supervision and validation requirements.

### 2.1 Components and checkpoint representation

The release uses a shared safetensors index with namespaced tensors. The
inspected checkpoint contains 16 weight shards and 2,131 tensors
distributed across eight components (Table 1). A strict reader resolves
the component namespace and checks tensor availability. This
organization supports component-wise loading and explicit precision
accounting; it does not imply that all components share parameters or
that an unmodified generic model loader can execute every task.

### 2.2 Visual-language backbone

The language, vision, and tokenizer components originate from
Qwen3.5-4B \[14\]. The language backbone has 32 layers, hidden width
2,560, and intermediate width 9,216. Its hybrid attention layout
contains 24 linear-attention layers and eight full-attention layers,
with one full-attention layer following each group of three
linear-attention layers. The configuration specifies 16 attention heads
and four key/value heads. The vision encoder has 24 layers, hidden width
1,024, output width 2,560, and patch size 16.

The vision projection produces representations at the language
backbone’s width, allowing image content and the user’s question to be
processed in the same conversational context. The processor supplies
image patches and positional information; the language decoder then
generates the textual response. The interface supports image
description, questions about visible text, and extraction from charts or
tables through the same generation path.

### 2.3 Temporal speech connector

The inherited speech-recognition component belongs to the Qwen3-ASR
family \[11\]. Its retained audio configuration uses a 24-layer encoder
with model width 1,024, 128 mel bins, and 16 attention heads. The
temporal connector operates on the extracted 2,048-dimensional features;
the connector input dimension and the encoder’s internal model width
refer to different interfaces. Upstream speech-recognition results are
not measurements of this composed checkpoint.

Let $`H\in\mathbb{R}^{T\times 2048}`$ denote the connector input. A
layer-normalized bottleneck maps each frame to width 256:

```math
U_{0}=\operatorname{GELU}\!\left(\operatorname{LN}(H)W_{\mathrm{down}}+b_{\mathrm{down}}\right). \tag{1}
```

Two depthwise temporal convolutions with kernel size five use dilations
one and two, respectively. Each is followed by feature mixing and a
residual connection. Padding preserves the frame count $`T`$. An output
projection returns the bottleneck representation to width 2,048:

```math
\widetilde{H}=H+U_{2}W_{\mathrm{up}}+b_{\mathrm{up}}. \tag{2}
```

Here $`\operatorname{LN}`$ denotes layer normalization and
$`\operatorname{GELU}`$ denotes the Gaussian error linear unit. The
output branch is zero-initialized in the connector definition, giving an
identity residual at initialization; this is an initialization property
rather than a claim that the final learned branch remains zero. A
separate layer-normalized multilayer projection maps the result into the
2,560-dimensional language space. A connectionist temporal
classification (CTC) readout is used in the training implementation and
does not act as a semantic routing gate at inference.

Preserving the frame sequence allows the language projection to consume
temporally resolved acoustic features. The dilated residual blocks
expand the temporal receptive field while the bottleneck limits the
width of the trainable branch. The acoustic encoder, temporal
adaptation, and language projection therefore have distinct roles in the
speech-input path.

### 2.4 Speech generation and custom voices

Speech output is conditioned on the response text. The speech generator
converts text into sequences of acoustic codes, and the codec
reconstructs waveform segments from those codes. The generator has 28
layers with hidden width 2,048 and uses 16 speech-code groups. Keeping
generated text as an explicit intermediate representation allows the
application to present the same response in written and spoken form and
to schedule synthesis as text segments become available.

Custom voice conditioning supplies an x-vector extracted from a
reference recording to the speech generator. The interface accepts
finite mono recordings of one to 30 seconds and does not require
per-speaker retraining. This separates the linguistic content, specified
by the response text, from the speaker condition, specified by the
reference utterance. The conditioning vector is attached to the
synthesis request so that separate conversations can use different
references.

For incremental delivery, the text segmenter releases sentence-sized
units at sentence boundaries, eligible soft separators, or a maximum
buffer of 48 characters. Decimal points are distinguished from sentence
endings. The codec reconstructs successive waveform chunks using
retained left context and discards samples already delivered. Chunk size
and context length are runtime settings; the speech experiments
distinguish native and reference configurations. Bounded queues and
cooperative cancellation coordinate text generation, synthesis, and
playback.

### 2.5 Candidate Decisions and Structured Interaction

#### 2.5.1 Task-conditioned candidate scoring

The decision interface accepts two to 151 supplied candidates and a task
identifier that selects one of three task-specific scorers. For a
candidate representation $`h_{i}\in\mathbb{R}^{2560}`$ and task $`t`$,
the corresponding linear head computes

```math
z_{i}=w_{t}^{\top}h_{i}+b_{t},\qquad\hat{\imath}=\arg\max_{i}z_{i}. \tag{3}
```

The heads contain three weight tensors and three bias tensors. Their
outputs are relative candidate scores, not calibrated probabilities of
physical success. Candidate sets and their interpretation are
application inputs; selecting a candidate does not directly actuate a
device.

The task identifier selects the scoring head while the supplied
candidate set determines the available alternatives. Returning both
scores and the selected index allows an application to inspect the
ranking and apply its own acceptance policy. The head does not create an
alternative outside the supplied set.

#### 2.5.2 Tool calls, schemas, and execution boundaries

The application interface supports tool calls and JavaScript Object
Notation (JSON) Schema outputs. A request supplies the available tool
definitions or the required response schema; the language model
generates the associated name, arguments, or structured fields. Parsing
and schema validation check the representation before it is passed to
the application. Candidate scoring complements this generative interface
when the alternatives are already enumerated.

Open-ended dialogue is interpreted by the language model using committed
conversation history. It is not intercepted by keyword lists or fixed
identity replies. Deterministic checks instead govern authentication,
wire formats, bounds, request cancellation, duplicate protection, and
action authorization. This separation permits natural references in
conversation while keeping actual device execution subject to an
application control gate.

## 3 Training and Checkpoint Assembly

### 3.1 Inherited components and bounded component training

Training is component-specific. The visual-language backbone and
acoustic encoder inherit their foundation-model training. Speech
generation and codec components originate from Qwen3-TTS-12Hz-1.7B-Base
and its speech stack \[15, 16\]. Local component training addresses the
acoustic–language interface and candidate scoring. Table 2 separates
these optimization stages from checkpoint assembly. No new joint
foundation-model pretraining stage is introduced.

| Stage                 | Optimization / frozen components                                     | Role in the system                                          |
| --------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------- |
| Inherited foundations | Upstream language, vision, acoustic, and speech objectives           | Perception, language generation, and speech synthesis       |
| Temporal connector    | Answer-token likelihood plus 0.1 CTC; language backbone frozen       | Temporally resolved acoustic–language adaptation            |
| Candidate heads       | Candidate-distribution cross-entropy; task-specific linear scorers   | Ranking supplied alternatives for each task                 |
| Checkpoint assembly   | Namespace consolidation and precision restoration; no optimizer step | A self-contained checkpoint with explicit component loading |

Table 2: Training and assembly boundaries. Recipe information is
distinguished from measured quality of the assembled release. The
component experiments are not a controlled ablation of the complete
system.

The retained temporal-connector training implementation keeps the
language backbone frozen and combines answer-token negative log
likelihood with an auxiliary CTC objective:

```math
\mathcal{L}_{\mathrm{speech}}=-\sum_{t\in\mathcal{A}}\log p_{\theta}(y_{t}\mid y_{<t},\widetilde{H})+0.1\,\mathcal{L}_{\mathrm{CTC}}, \tag{4}
```

where $`\mathcal{A}`$ contains answer positions rather than prompt or
padded positions. The implementation uses FP32 optimizer states and CTC
loss with a differentiable BF16 serving forward. The auxiliary CTC
readout supports alignment training and is not an inference-time intent
gate. This source-level recipe is not an ablation showing a gain for the
released connector, nor a fresh speech-quality score for the complete
checkpoint.

The retained bounded connector recipe specifies 2,048 steps, batch size
four, and AdamW optimization. Peak learning rates are $`10^{-5}`$ for
the base projection, $`10^{-4}`$ for the temporal branch, and
$`3\times 10^{-4}`$ for the auxiliary CTC readout. This description
records the historical recipe without promoting its development-set
observations to an official speech benchmark. Establishing connector
utility requires a paired evaluation with the same acoustic inputs and
backbone, together with a documented mapping from the evaluated
connector to the release.

### 3.2 Candidate-head supervision

For each supplied candidate set, head training minimizes cross-entropy
between a target distribution and the softmax over candidate scores.
Checkpoint selection uses equal-task macro cross-entropy across choice,
noul, and score, giving each task equal weight despite different sample
counts. The component experiment uses its paired frozen reference
backbone. Section 5.3 reports that validation separately from evaluation
with the assembled release.

### 3.3 Assembly and precision verification

Assembly resolves each component namespace into a shared safetensors
index. Tensor counts, shapes, source bindings, and precision-restoration
receipts provide loading evidence. They do not prove end-to-end
conversational quality. For native evaluation, 723 language and vision
tensors are copied into a backend-compatible view and checked against
the release; 48 original FP32 language parameters are restored exactly
after loading. The view serves evaluation and does not replace the
complete eight-component package.

## 4 Experimental Design

### 4.1 Evaluation questions

The experiments separate task correctness from interface implementation
and inference capacity. We first test whether the assembled system can
answer knowledge and reasoning questions, follow explicit instructions,
and extract information from images, then place these results alongside
published evaluations of related models. We examine the two
structured-output interfaces: ranking supplied alternatives and
generating tool calls. We also inspect archived speech-delivery traces
to distinguish response startup from waveform production, and measure
whether long responses can finish under concurrent execution without
exhausting the key/value (KV) cache. Table 3 links each question to the
corresponding task and metric.

Two design choices are central to the study. First, general task scores
and application-specific decisions are evaluated separately because they
exercise different outputs and scoring rules. Second, restricted
generation and long-thinking generation are treated as distinct
protocols. Saved-answer diagnostics examine how output limits and
extraction failures affect interpretation; they are not used to infer a
component’s causal contribution. Speech quality and physical-device
outcomes require additional measurements beyond these text, image, and
decision tasks.

| Question                                 | Task and scope                                                                                  | Measurement                                                           |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Knowledge and reasoning across domains   | MMLU-Pro \[18\]: 12,032 restricted-protocol questions; 3,000 stratified long-thinking questions | Answer accuracy and subject-level variation                           |
| Instruction and mathematical constraints | IFEval \[23\]: 541 prompts; MATH-500 \[6\]: 500 problems                                        | Strict/loose compliance; verified final answers                       |

### 4.2 Tasks, samples, and metrics

##### Text reasoning and instruction following.

MMLU-Pro \[18\] supplies 12,032 questions across 14 subjects and
official prompt-formatting and answer-extraction helpers. The restricted
protocol evaluates the full set. To bound the cost of long-thinking
evaluation while preserving subject coverage, we select a fixed
3,000-question proportional stratified subset. Subject quotas use the
largest-remainder method; within each subject, a fixed seeded hash of
question IDs determines selection. Neither answers nor model correctness
enter the selection rule. The subset score is therefore reported with
its own denominator, separately from the full-set score.

IFEval \[23\] evaluates compliance with verifiable instructions using
all 541 official prompts and the official strict and loose checkers. We
report both prompt-level compliance, which requires all instructions in
a prompt to pass, and instruction-level compliance. MATH-500 \[6\] is a
500-problem subset of the MATH test set \[4\]; we evaluate all 500
problems. Prompts request a step-by-step solution ending in a boxed
answer; Math-Verify 0.9.0 \[5\] checks the final answer. These tasks
distinguish formatting constraints from mathematical answer correctness.

##### Visual understanding.

MMMU \[22\] tests image-grounded reasoning using all 900 public
validation questions, with 30 examples in each of 30 subjects. We use
the official response parser and deterministic per-ID fallback and
retain subject-level counts. ChartQA \[8\] tests chart reading and
associated reasoning on the available 1,920-example public validation
split, evenly divided between human-authored and machine-generated
questions. Scoring uses the relaxed answer criterion, and both groups
are reported to reveal differences hidden by the aggregate. These are
public-validation measurements, not hidden-test leaderboard scores.

##### Candidate decisions and function calls.

JevBench \[2\] evaluates typed decisions on 231 public examples.
Features are generated by the assembled language backbone and scored by
the retained FP32 candidate heads. We compare normalized states against
the checked training states to detect exact overlap; this check does not
establish semantic independence or absence from foundation pretraining.
The public-subset accuracy is distinct from the sealed-board composite
score. We also report the historical head-validation experiment with its
paired frozen reference backbone to examine variation among the three
scoring tasks; its 3,202 examples use the recorded target-tie accuracy
criterion and cross-entropy.

The Berkeley Function Calling Leaderboard (BFCL) \[10\] tests generated
function selections and arguments. Our scope comprises 3,641 single-turn
cases in 13 categories, including simple, multiple, parallel, relevance,
and irrelevance cases. Multi-turn and agentic categories are excluded.
Category-specific checkers assess function-call correctness, while
missing final responses remain in the denominator. The resulting scope
must not be labeled the complete BFCL v4 overall score. Appendix C
describes the absent-tool normalization required for a uniform
saved-answer rescore.

### 4.3 Generation protocols and answer preservation

The restricted protocol uses greedy decoding and an 8,192-token context.
IFEval and MATH-500 use a non-thinking chat template with output budgets
of 2,048 and 4,096 tokens, respectively. The MATH prompt still requests
explicit reasoning in the answer text. Restricted MMMU and ChartQA
generation allows 1,024 new tokens and uses a declared image-pixel
budget of 1,048,576. These IFEval, MATH-500, and ChartQA measurements
are retained without a long-thinking rerun.

Restricted MMLU-Pro uses a raw completion prompt with up to five
same-subject chain-of-thought exemplars. An input-budget rule removes
exemplars when the formatted prompt reaches 2,048 tokens. Generation
allows 2,048 new tokens and stops at the configured next-question
delimiter; unparseable answers count as incorrect. This length-adapted
setup differs from an unmodified five-shot prompt.

The long-thinking protocol keeps all five MMLU-Pro exemplars, uses a
131,072-token context, and allows 32,768 new tokens for MMMU, MMLU-Pro,
and BFCL. Sampling uses temperature 1.0, top-$`p`$ 0.95, top-$`k`$ 20,
minimum-$`p`$ 0, and presence penalty 1.5. Visual inputs retain original
images and source-processor defaults. Only the final response after the
thinking delimiter is scored. A fixed per-ID seed defines one response
per question; completed answers are not regenerated to select a better
response. The settings define our experiment and do not establish exact
parity with a vendor’s prompts, repetitions, or leaderboard aggregation.

For MMLU-Pro, 624 completed answers selected by the frozen subset
manifest are reused byte-for-byte and the remaining 2,376 are generated
once. Resumed MMMU stages follow the same preservation rule. Retained
answers contribute to capability denominators, but their previously
generated tokens and elapsed time are excluded from a later stage’s
throughput. Output limits, missing final delimiters, and unparseable
answers are recorded alongside accuracy rather than removed from the
scored set.

### 4.4 Comparison with published model evaluations

We use author-published technical reports and official model cards to
place the results in context, with Qwen3.5-4B as the direct
visual-language foundation \[14\]. Other comparison models have a
similar language-backbone scale. An active-parameter count for a
mixture-of-experts model is not treated as the total size of a dense
model. None of the comparison models is rerun in this study.

For each source, we record the model version, task, available split
information, and evaluation mode. Tables identify stratified and full
samples, prompt-level instruction compliance, and the included
function-calling categories. Missing source details are marked as
unspecified. Comparisons are presented by task, without constructing a
composite rank.

### 4.5 Speech-delivery measurements

Speech startup and complete-response timing answer different questions
from aggregate text throughput. We inspect existing local HTTP traces on
NVIDIA GB10. For the merged checkpoint, a short fixed-text synthesis
request uses the three-stage native backend after earlier synthesis and
visual requests have warmed the service. For longer conversational
traces, a separate pre-merge reference runtime uses a text prompt or a
prerecorded synthetic utterance paired with an image. These two runtime
configurations are reported separately. Each selected scenario has one
recorded observation; there is no repeated-trial latency distribution or
controlled cold-start comparison.

Timing begins immediately before the client issues the request. First
pulse-code modulation (PCM) latency ends when the client receives its
first audio event; completion ends at the final event for native
synthesis and at HTTP-stream closure for the reference runtime. Audio
duration is the number of waveform samples divided by sample rate. We
define the request-level real-time factor (RTF) as completion time
divided by output-audio duration. Inter-chunk gaps and replayed
playback-buffer events describe delivery continuity. The
synthetic-audio-and-image case includes the request’s recognition, image
processing, response generation, and synthesis, but excludes recording
time and input creation. None of these traces measures the interval from
a physical speaker’s last utterance to audible loudspeaker playback, or
latency over a remote network.

### 4.6 Inference experiment design

All native text and visual inference measurements use NVIDIA GB10 and
vLLM 0.33. The main backbone runs in BF16, with its 48 source FP32
language parameters restored after loading. JevBench uses the reference
backend and is excluded from native-engine throughput comparisons. We
report the execution path separately because native language generation
and complete spoken interaction exercise different components.

##### Why measure both windows and complete responses?

Fixed windows measure how rapidly an engine produces tokens while many
requests are active. They may end before the longest requests consume
their full cache or finish their answers. We therefore use three
complementary workloads: a concurrency sweep with 30-second warmup and
90-second measurement windows; fixed batches that drain to natural
completion; and sustained admission with cache and preemption telemetry.
In the short sweep, only the probe’s own unfinished requests are
canceled at a boundary. In complete-response experiments, requests
retain their original generation budgets and finished answers remain
saved.

Aggregate output throughput is

```math
R_{\mathrm{agg}}=\frac{\sum_{j=1}^{N}n_{j}}{t_{\mathrm{generation}}}, \tag{5}
```

where $`n_{j}`$ is the generated output length and the interval includes
prompt processing, scheduling, output handling, interleaved checking,
and the final response tail. Initial model loading and separate
post-generation rescoring are excluded. Complete-batch and
complete-stage measurements use saved outputs; fixed windows include
in-flight tokens and are labeled separately. We additionally record
actual running requests, KV occupancy, preemptions, length-limited
outputs, and missing final responses.

##### Admission under context growth.

Dynamic cache allocation and sharing reduce redundant storage \[7\], but
admitted requests continue to grow after new intake pauses. The
evaluated admission policy therefore combines observed allocation with
estimated future demand. Let $`B`$ be the physical pool size, $`A`$ its
observed allocated blocks, $`C`$ the lease for newly admitted prefills,
$`F`$ the further-growth and scratch estimate for acknowledged requests,
and $`G`$ a publication guard. The estimate is

```math
\widehat{B}=A+C+F+G. \tag{6}
```

Shared physical allocation is counted once in $`A`$. A prefill remains
charged for its prompt and a forecast output window until it has
streamed output and is at least ten seconds old. An acknowledged request
leases 1,024 further tokens, bounded by its unchanged remaining budget,
plus recurrent-state scratch and one publication block. The global guard
is 32 blocks. These leases are refreshed as outputs grow and do not
reserve every possible remaining token.

The policy uses $`B=2{,}048`$ blocks, a working level of
$`\lfloor 0.85B\rfloor=1{,}740`$, and a usable level of
$`\lfloor 0.90B\rfloor=1{,}843`$. KV capacity is 36 GiB, the CUDA
allocator cap is 48 GiB, and the process-memory limit is 90 GiB. The
request target starts at 64 and can rise to 128. Intake pauses at
observed KV occupancy of 75%, stale telemetry, sustained waiting
pressure, or a new preemption; active requests retain their budgets. A
fixed initial batch is filled and then drained without replacement
admissions to check complete-response behavior before evaluating
continuous refill. Memory limits share one physical-memory platform, and
the growth estimate is not a worst-case memory guarantee.

## 5 Results and Analysis

The results address task capability, variation within tasks, and the
conditions under which a throughput measurement remains useful.
Protocols and sample sets are kept explicit throughout: a score
describes its declared workload, while protocol changes and component
changes require separate interpretation.

### 5.4 Inference capacity under growing responses

#### 5.4.1 Short-window throughput and sustained cache pressure

The visual concurrency sweep reaches 8, 16, 32, 64, 128, and 256 actual
scheduled requests. Its corresponding 90-second rates are 178.81,
314.81, 490.00, 718.11, 940.81, and 1,020.65 output tokens/s. More
active requests improve token production within these windows. However,
a subsequent fixed 256-request run reaches 99.62% occupancy of its
32 GiB KV cache and accumulates 675 preemptions before termination. The
highest measured short-window rate therefore does not establish a stable
operating point for long responses.

This behavior is consistent with continued context growth after
admission: already active requests consume additional cache even when
intake pauses. A high window rate measures productive computation during
that window, while sustained completion also depends on whether the
accumulated contexts fit. The result motivates the growth-aware
admission experiment in Section 4.6, rather than selecting concurrency
from the highest short-window rate alone.

#### 5.4.2 Complete batches and the final response tail

With 32 GiB KV cache and a 48 GiB CUDA allocator cap, a complete
128-request text batch generates 775,019 tokens in 1,659.47 seconds
(467.03 tokens/s); an eight-request visual batch generates 28,633 tokens
in 615.16 seconds (46.55 tokens/s). Both complete without preemptions,
length-limited outputs, or missing final responses, and saved token
totals match engine counts. The text batch reaches sampled peak KV
occupancy of 67.89% and CUDA allocation of 41.25 GiB. These measurements
include the tail in which only the longest responses remain active.

Under the physical-usage and growth-lease policy, a separate initial
batch of 128 new MMLU-Pro answers produces 834,117 saved output tokens
in 1,403.27746 seconds, or 594.41 tokens/s. Independent checks match
saved tokens to the engine counter difference and find zero preemptions,
length-limited outputs, and missing final responses. Previously
completed source answers remain unchanged. Sampled peak KV occupancy is
66.63%. Figure 4 shows cache growing while few answers are complete,
then draining as long responses finish; both phases contribute to the
reported wall time.

This trace establishes completion for the measured batch. Replacement
admissions are disabled during its drain, and the examples come from one
MMLU-Pro prefix. It therefore does not establish stability under
continuous refill or across workloads. Likewise, differences in prompts,
cache settings, output lengths, and timing windows prevent interpreting
594.41 tokens/s relative to the preceding rates as an isolated policy
speedup.

For the 445 fresh MMMU answers, saved output and the drained engine

by output-completion checks and a declared workload. Historical

### 5.5 Streaming speech latency and delivery

Table 7 separates the merged model’s short synthesis trace from the
pre-merge reference runtime’s conversational traces. In the merged-model
case, the first PCM chunk arrives after 0.390 s and the final event
after 1.305 s. Four chunks contain 2.48 s of audio, yielding a
request-level RTF of 0.53. This is a warm text-to-speech observation
with fixed input text: language-response generation and speech
recognition are not part of that request. The script’s earlier
full-waveform synthesis request takes 5.701 s for 2.72 s of audio.
Different request formats and execution order prevent treating these two
observations as a controlled cold-versus-warm comparison.

The reference runtime generates a 19.60 s spoken reply to a text prompt,
receiving the first PCM at 1.160 s and completing the request at
16.494 s. With prerecorded synthetic speech and an image, first PCM
arrives at 4.544 s and completion at 29.460 s for 29.76 s of output
audio. First text events occur at 0.119 s and 3.604 s, respectively. The
multimodal path includes more processing stages, but different inputs
and response lengths prevent attributing the latency difference to one
stage.

Maximum audio-arrival gaps are 1.018 s and 1.004 s for these two
reference cases. Replaying their saved arrival traces through the
adaptive player produces no buffer underruns. A separate real-model
request in a headless Firefox browser records first PCM reception at
1.28 s and a scheduled audio-context start at 1.31 s, also with no
counted underruns. Scheduled playback and trace replay do not establish
physical speaker output or perceptual quality. Although each tabled
request has an RTF below one, sustained interaction also depends on
startup delay, arrival variability, buffering, and subsequent turns.
These single cases support streaming feasibility, not a percentile
latency claim or a speed ranking against other models. In particular,
the theoretical cold-start first-packet value reported for
Qwen3-Omni \[20\] has a different timing definition and is not a matched
comparator.

## 6 Discussion and Limitations

The experiments support two observations about evaluating a modular
system. First, task-level aggregates conceal variation: MMMU subjects,
ChartQA question sources, and candidate-head tasks show different error
rates. Second, measurement conditions influence what a result can
establish. A changed generation protocol cannot isolate a component’s
contribution, and a short throughput window cannot establish completion
under sustained cache growth. Keeping sample selection, generation,
scoring, and timing explicit makes these distinctions testable.

##### Attribution and comparison.

The pretrained visual-language and speech components supply substantial
inherited capability. The published comparisons contextualize the
scores, but do not quantify capability retained or lost during assembly.
A matched control would hold prompts, image processing, seeds, and
checkers fixed while changing only the base or assembled checkpoint. A
separate connector study would hold the acoustic inputs and language
backbone fixed. These controls are needed to evaluate the contribution
of local adaptation; neither the training recipe nor successful
component loading supplies that evidence. Our broader speech and
candidate-scoring interfaces also require additional stored components,
so comparison at language-backbone scale is not a comparison at equal
total system size.

##### Coverage and scoring.

The long-thinking MMLU-Pro result covers a proportional 3,000-question
subset, while BFCL covers only single-turn cases. Independent final
MMLU-Pro rescoring and uniform BFCL saved-answer rescoring remain
outstanding. IFEval, MATH-500, and ChartQA retain their
restricted-protocol measurements. The study provides single-run
observations, without repeated-run confidence intervals or same-protocol
peer-model comparisons. Public task scores and historical head
validation also leave semantic training overlap and performance on
unseen application states unresolved.

##### Speech and interactive behavior.

The speech traces establish specific delivery behavior, not general
speech quality. Recognition error, spoken-content fidelity, speaker
similarity, and perceptual naturalness need their own evaluations. The
merged-model latency result concerns one warm fixed-text synthesis
request, whereas the longer conversational traces precede checkpoint
merge and use a separate reference runtime. Neither supplies
microphone-to-speaker latency, cold/warm percentiles, or a controlled
comparison with an end-to-end speech model. Existing functional checks
of reference-voice synthesis and subsequent requests also do not
establish speaker similarity or cancellation-response time. Native text
and visual benchmark results do not constitute full speech-path
acceptance.

##### Systems and application scope.

Inference results are limited to one GB10 platform and the declared
workloads. The growth leases estimate future demand and do not guarantee
a worst-case memory bound; repeated sustained runs are needed to
characterize robustness. At the application boundary, a candidate
ranking or valid tool call remains an advisory output. Physical
execution depends on authorization, current device state, and client
validation. No device intervention or clinical study is reported, and no
clinical or autonomous-action safety conclusion follows from the
benchmark results.

## 7 Conclusion

DRVEXO-4B-Unified combines visual-language reasoning, temporally adapted
speech input, reference-conditioned speech output, and
supplied-candidate scoring in an independently loadable checkpoint. Its
independently rescored MMMU validation score of 74.22% exceeds the
reported validation scores of Gemma 3 4B IT and InternVL3.5-4B without
test-time scaling. Its IFEval and MATH-500 scores also exceed the
corresponding original Qwen3-4B non-thinking reports. Streaming speech
synthesis achieves a first-chunk latency of 390 ms on GB10, while a
complete 128-answer text batch reaches 594.41 output tokens/s without
preemptions. These results characterize a system that combines
multimodal communication with structured application interfaces. Further
work will extend speech-quality evaluation, component studies, and
sustained-load measurements. Model weights, code, and redistributable
evaluation artifacts are planned for public release, with the model and
code under Apache License 2.0 and applicable upstream terms retained.

empty tool lists among the 3,641 inputs. The installed parser request
wrapper rejects an empty tools array together with automatic tool
selection before parsing a response. A separate adapter omits both
request fields only when no tools are supplied. CPU checks preserve the
request fields for nonempty-tool representatives of all 13 categories
and preserve positive and negative official-checker controls; a missing
thinking delimiter remains invalid.

All 3,641 answers have been generated, but uniform saved-answer
rescoring and independent verification remain pending; no corrected BFCL
accuracy is available. The original run and its 78.85% score are
preserved. Final acceptance requires unchanged answer text, IDs, order,
token counts and stop reasons; any scoring change must be restricted to
the four absent-tool cases with the recorded request-schema exception.
The verification must compare source and corrected-output hashes and
enumerate the changed cases. It must not regenerate or select responses
again.
